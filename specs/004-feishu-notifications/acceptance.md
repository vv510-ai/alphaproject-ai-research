# 第十一课：飞书通知通道与收件核验

日期：2026-10-18。范围：本机学习工程 `AlphaProject-Lab` 的手动通知测试。实现与真实发送已完成，**用户已反馈实际收到；网页核验码尚未提交**。收件反馈与网页保存的核验时间分别记录。

## 这一课在做什么，为什么这样做

通知通道就是系统把消息送到你能看到的地方的出口。今后“发现异动”和“生成简报”负责决定要说什么，本课负责把消息交给指定飞书群，并留下处理结果。

可以沿着一条路线理解：**网页点击 → 后端核对接收群 → 先保存测试记录 → 发给飞书 → 保存回执 → 你在飞书查看 → 回网页确认收件。**

“发送成功”容易说得过头，所以本课拆成两个独立事实：

- **飞书已接收**：接口返回成功和消息标识，表示平台接受了这次发送。
- **你已确认收到**：把这条飞书消息中的 6 位核验码填回网页，服务器核对通过后才记录确认时间。这个码由学习工程随机生成，只用于本条测试，不是飞书登录密码。

## 你参与的配置决定与实际接收目标

用户要求“发到只有我自己的群里”，随后明确“我的原来的项目文件就已经配置好了，直接搬过去”。因此没有让用户重新建机器人，也没有复制整个原项目。

只读取原 `AlphaProject/.env` 中 4 个飞书字段：应用标识、应用密钥、接收群标识、接收标识类型。原文件不改写；没有复制其他配置、数据库或虚拟环境。实际复用的是**应用机器人**，不是群自定义 Webhook。

原群的只读查询和导入时查询均通过：**群名“量化推送”，机器人“vv小助手”，私有群，1 位成员、1 个机器人，唯一成员与群主一致。**配置绑定了这位成员；每次提交测试前重新核对，群成员或相关条件变化则停止发送。这里不在文档展示真实群 ID、成员 ID 或密钥。

必要配置使用 Windows 当前用户的 DPAPI 加密，保存在 `.runtime/feishu-config.dpapi`；浏览器接口不返回秘密值，也不返回核验码或其哈希。服务器启动时才读取加密配置。这个文件依赖本机 Windows 用户环境，不能把复制该文件等同于跨机恢复。

## 现在怎么操作

1. 打开或刷新[电脑入口](http://127.0.0.1:18765/)。手机与电脑处于同一 Wi-Fi 时可用[局域网入口](http://10.45.146.38:18765/)，仍需保持电脑服务运行。
2. 点击“飞书通知”，确认接收群为“量化推送”。初始开关默认关闭，开启时会先核对目标。
3. 点击“发送一条测试”，等待出现发送记录。消息有学习工程标记、完整记录标识、北京时间和核验码，不是股票异动。
4. 到飞书查看相同记录标识的消息，把 6 位核验码填入对应网页记录下，点击“确认我已收到”。可以保留前导零。
5. 已有本课助手示范发送的一条消息，可直接完成第 4 步，无须再发。若确实需要另测，间隔至少 30 秒；界面会显示可再次测试的时间。

**本次真实示范：**助手通过真实页面点击“开启通知”和“发送一条测试”。记录 `c9596a76-114a-4346-9d82-650d60496ec2` 创建于北京时间 **2026-10-18 03:06:29**，飞书接收结果保存于 **03:06:32**。电脑页和局域网页面均显示同一记录，状态“飞书已接收”。助手没有读取或填写真实核验码。

**用户参与结果：**用户于 03:23:19 又主动发出记录 `245118fa-cb93-47a5-8c2c-31f93f0b4f71`，平台于 03:23:22 接收。随后用户反馈“已收到，并在网页确认成功”；发现后端确认时间仍为空后进一步核对，用户明确“显示‘收件尚未确认’，我还没填码提交”。因此可确认消息实际收到，但不能把网页核验记为已完成。用户应将 03:23 消息的核验码填到对应记录下，不混用先前 03:06 的记录。见[用户收件反馈](../../evidence/feishu-20261018/user-receipt.json)。

只回查本条已发送消息的额外诊断返回 HTTP 400 / 飞书错误码 99991672，涉及 `im:message` / `im:message:readonly` 读取权限。因此没有取得远端正文回读证据，也没有新增权限或重发消息；这与发送接口的 accepted 结果分别记录。实际收件仍由用户查看并回填确认，不能用这次读取失败推定消息未发出。

## 用了哪些工具

| 工具 | 在本课承担什么工作 |
| --- | --- |
| 原项目配置与官方飞书接口 | 复用已设定的应用机器人和单人群；核对身份、提交文本消息 |
| HTTPX | 后端发 HTTPS 请求；固定飞书域名，限制等待和返回体，不自动重试发送 |
| Windows DPAPI | 把必要配置加密保存在本机，避免浏览器和仓库取得密钥 |
| FastAPI | 接收页面的开关、测试、核验操作；把一次测试交给后台处理，页面读记录跟踪结果 |
| SQLite | 新增通知设置和消息记录；原自选、报价、日线保持原样 |
| React / TypeScript / Vite | 做通知面板、状态提示、收件输入与窄屏布局 |
| pytest / Chrome DevTools | 检查失败与并发情况，并真实打开网页操作、观察布局和状态 |

没有增加 SDK 或其他依赖，没有新增模型调用、定时任务或收费服务。

## 如何处理失败、关闭和重复操作

- 同一个请求号重复提交，只读回原记录，不再发一条；一次只处理一条测试，30 秒间隔防连点。
- 群不符合约定或平台明确拒绝，记录失败；发送后超时、回执不完整等记“结果待核对”，不会自动重发。
- 关闭通知会取消尚未提交的测试；已经发送中的请求可能仍送达。再开启不会补发取消的记录。
- 两端同时开关时，迟到的旧开启结果不能覆盖后来已完成的关闭。此问题在独立审查中实际复现后修复，并用两线程受控用例复验。
- 重启时，未提交的任务取消；已经进入发送阶段但没有结果的任务变为未知。没有启动后重放发送的逻辑。
- 页面刷新只读已保存状态，不重新发送；错误提示需要主动关闭，不会被成功轮询悄悄清除。
- 本课尚无自动事件队列；事件过期 M、交易日历、自动任务恢复等仍留到异动/简报阶段，不据此关闭整条 AC-004。
