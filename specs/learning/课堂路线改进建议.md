## 3. 产品上优先做深哪一处

建议把已有“AI 解释 + 异动提醒”做成第一项重点：**用户看到一条变化时，能知道发生了什么、依据在哪里、哪些尚不能确定，并能追到这条提醒的处理结果。**它可以沿用当前六个功能，不需要现在增加新模块。

| 现有功能 | 推荐加深的行为 | 可检查结果；目前均待实现 |
| --- | --- | --- |
| 行情看板 | 价格旁有来源时间、来源和可用状态；来源失败保留旧值时明确标记 | 旧行情、时间缺失和网络失败不会显示成刚更新 |
| 异动检测 | 同一次触发有稳定事件 ID，保留规则与当时数据 | 重复轮询不会产生重复事件；重启后状态和已知发送记录仍可查 |
| AI 解释 | 分开“可核对事实、可能解释、缺少证据”；事实能回到实际输入 | 仅有价格时不会编造同期新闻、资金流或因果结论 |
| 通知 | 提醒带事件和依据时间；成功、失败、未知分开 | 页面记录与真实消息能对应；超时不假报成功或无限重发 |
| 早盘简报 | 标出使用哪一天的数据、哪些股票/来源缺失、何时生成 | 数据不齐仍能清楚说明覆盖范围，不能把空项补成正常结果 |
| 自选与详情 | 电脑和手机读取同一份记录，入口围绕当前任务组织 | 用户能独立完成增删、找变化、看依据，刷新和重启不丢 |

一个具体例子：我们已有 2026-10-16 晚间报价，来源时间为 16:14:47，接收时间约 22:02，价格 1329.00 元、涨跌幅 +1.22%。它支持描述这份报价及其时间，不能单独证明“某条利好导致上涨”。改进后的预期输出应保留这些事实，并说明缺少同期原因证据。这是验收示例，**不是已经运行模型得到的合格答案**。[原始样本](../../evidence/data-source/spot-600519-20261016T220152725509.json)

如果只选一个进阶重点，我建议选上述“能查依据的异动解释”，因为它同时练习数据、规则、提示词、界面表达与效果评价。多智能体、向量库、自然语言选股等留作满足具体需求后的扩展，当前不自动加入。

## 4. AI 功能要补一组固定案例

“固定案例”就是把输入和检查标准保存下来，同一批材料分别跑修改前后的提示词，观察哪类问题改善、哪类退步。先人工核对少量代表性案例，有重复评测需求时再接工具。

| 案例类型 | 需要检查的行为 |
| --- | --- |
| 正常完整数据 | 股票身份、数值、时间和引用与输入一致；不用模糊套话代替已有事实 |
| 晚间旧值、来源时间缺失或倒退 | 清楚标注时间与不确定性，不因为本机重新请求就当成新行情 |
| 只有行情，没有新闻/公告 | 说明可观察变化，但不编造新闻或确定原因 |
| 新闻属于同名公司、另一代码或另一日期 | 不错误归给当前股票，保留核对结果 |
| 多个来源互相冲突 | 显示冲突与采用依据，不悄悄挑一个凑完整答案 |
| 数据源或模型超时 | 保留基础事件与真实失败，不能生成替代价格或假称分析/发送成功 |

真实采样、人工标注、合成故障分别标记。先覆盖会造成误解的失败机制，再根据结果补样，不用固定样本数量冒充覆盖充分。

评价至少分三层：

1. **链路是否通：**输入、输出格式、保存、失败和状态能否正确传递。
2. **内容是否有依据：**逐条核对重要事实与引用，记录无依据陈述、漏掉的缺失项和错误因果。JSON 合法和链接存在都不能独自证明内容正确；模型自评分只作辅助。
3. **对你是否有用：**在相同任务中记录寻找变化和查证所需时间、提醒是否有用、哪些内容被反复忽略。先记录基线，再谈改善，不先填“节省百分之多少”。个人重复使用记录不能外推所有用户。

同时保存输入样本、提示词版本、模型标识、生成结果、调用成本与耗时。改提示词时尽量固定其他因素；用于调提示词的案例与保留的核验案例区分，不能反复针对同一批调优后仍称独立评估。当前尚未创建这些评测样本集或调用模型，以上是实施建议。

## 7. 接下来怎样上课

当前几课花在调研与资料上较多。05 汇总后，把学习重点转向能实际操作的结果；仍保留课程的需求、架构、界面与工程准备，但围绕第一条路径完成必要部分。

| 阶段 | 这次要交出的东西 | 你参与的动作 |
| --- | --- | --- |
| 下一课：精简 PRD | 明确个人共享自选、关键功能边界与验收，记录未决项 | 决定会影响行为的选项，例如访问范围、第一类异动和通知目标；不用回答术语题 |
| 最小架构、界面和工程准备 | 能解释页面→接口→数据库的关系，有独立环境与启动入口 | 找到入口，看懂请求与保存结果分别在哪里 |
| 第一个功能：共享自选 | 真页面、真 API、真数据库的一条可用路径 | 在电脑添加，再刷新/重启后查看；条件具备时用手机读取 |
| 接入行情与事件 | 真实数据、来源时间、必要失败处理和可追踪事件 | 查看正常样本，再观察一次旧数据或失败场景的表现 |
| 通知与 AI 解释 | 真实送达记录、输入依据、固定案例的前后对比 | 核对一条提醒和一个解释，指出有用/误导的具体地方 |
| 简报、部署与迭代 | 核对数据日期、常开运行、版本和恢复，再记录使用反馈 | 从实际目标入口完成任务，按真实问题决定下一次改进 |

这些是建议节奏，不是要求一轮完成整个系统。每课优先做到“一次可观察操作、一个关键失败场景、一个能解释的取舍”；不为小改动机械增加测试或固定任务数。

后续可复用的开发指令示例：

> 先读当前决策和对应需求。本轮只完成指定的用户路径，开始前用通俗话解释输入、处理和结果。沿用已有选择，只调查会影响本轮的未知。实现后实际操作正常流程，并检查最相关的失败情况；保存、异步和通知要核对最终结果。最后给出操作入口，说明哪些已验证、哪些仍是替身或待验证，并让我参与一次有意义的操作。不要顺手增加其他功能。

本轮已经完成的是决策汇总、资料核验和这些改进建议。尚未修改课程原文或已安装 Skill，也未把进阶建议称为已经实现的产品能力。

## 8. 2026-10-20 执行节奏调整

用户反馈当前开发太慢，要求拆成几个任务并发，并询问课程原本是否这样安排。已重新核对本地保存的两份笔记和课程 `run-feature` 原始资产；课堂资料保持只读。

课程安排是：

- 四个独立主题的调研可并行，综合决策等材料齐备后完成：笔记二第 237–241 行。
- 任务需要标明并行组和依赖，同一功能内的前端、后端可并行：笔记二第 342、416 行，笔记一第 1137 行。
- 配置、迁移和接口契约按自身依赖排序，真正的端到端联调等前后端通过后执行：课程 `run-feature` 第 48–51 行。
- 课程采用单个完整功能收尾后再做下一个的节奏，明确反对同时实现多个完整功能：笔记一第 1198–1201 行、课程 `run-feature` 第 74–77 行。多个功能的文档准备理论上可隔离并行，与实现阶段的要求不是一回事：笔记二第 357 行。

本工程从这一轮起改为**按完整结果推进，内部任务并行**。前面的教学步骤拆得过细可以压缩；保留关键取舍和真实体验，不把小任务数当课程进度，不为每个例行检查再要一次用户回复。课程的单功能策略是可参考的方法，是否跨功能并行仍按实际依赖与文件冲突判断，不把课程模板当普遍禁令。

下一阶段可围绕已有“盘中数据与真实异动”缺口划分三个角色，不扩大六功能范围：

| 分工 | 主要工作 | 与其他分工的边界 |
| --- | --- | --- |
| 后端实现 | 持续采集、报价时效与证券状态资格判断，按已确认规则保存事件 | 独立服务模块；不自行改前端或发布；真实资格未证实前不直接打开真实提醒 |
| 前端实现 | 展示采集状态、最后成功时间、暂停和失败原因，使页面与实际后台状态一致 | 根据先约定的接口实现；不自行改数据库或后台任务 |
