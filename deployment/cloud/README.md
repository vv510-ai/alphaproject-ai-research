## 首次迁移（历史流程，现有站点不再执行 seed）

在项目目录使用 `.venv\Scripts\python.exe -X utf8 deployment/cloud/deploy.py`，依次执行：

1. `build`：完整本机测试、锁定前端依赖、类型检查、按 `/lab/` 构建；打印包记录路径。
2. `prepare --package <包记录.json>`：上传白名单代码包，校验后准备独立依赖，在服务器临时测试库运行完整检查。
3. `seed --package <包记录.json>`：读取学习版已授权的本机加密配置，确认没有未结束的任务，停止本机并获取数据库独占锁；仅向空的云端数据目录迁移一次。
4. `activate --package <包记录.json> --expected-current none`：数据库副本预检、最终备份、启动、核对实际进程和版本，再添加 Nginx 的 `/lab/` 转发。
5. `verify --package <包记录.json>`：验证 HTTPS、公开入口、前后端版本与文件哈希。仍需按本课验收验证实际业务操作。

凭据只经固定主机指纹 SSH 的标准输入传递，不进入代码包、命令参数或公开结果。程序包不包含 `.env`、数据库、密钥、虚拟环境、日志和课程原件。

`seed` 上传中断后，先用 `status --package <同一包记录.json>` 检查云端。再次运行同一 `seed` 会持有本机锁、校验原备份和本机数据未变，然后继续；已匹配云端初始迁移回执时直接读回成功，不覆盖数据。状态或哈希不一致时停止检查，不能删掉保护标记来强行继续。

## 后续发布和回退

普通功能修改完成后默认运行 `update`，无需逐次询问发布。它重新测试、构建、准备、在云端数据库副本上预检，备份后切换代码并复验公网，不上传本机数据库或配置。根目录 `部署网站更新.cmd` 和旧 `deployment/aliyun/deploy_update.py` 入口均已转接本命令，旧业务不会再启动。公网校验同时检查根版本一致、根入口 308 与原 API 的 GET/POST 410 退役响应。

统一后只能使用保留旧档案和预算承接的版本；服务器通过交接记录及活动库双重识别并拒绝不兼容旧包。下面的历史回退实验不代表 v0.10.x 可重新承担统一版业务。日常发布保留现有根路由和旧服务退役条件。

先 `status --package <已保存的包记录.json>` 查询正在运行的版本。回退使用目标旧版本的记录：

```text
activate --package <旧版本包记录.json> --expected-current <当前云端版本号>
verify --package <旧版本包记录.json>
```

只有已准备且文件校验通过的版本可切换。旧程序先在当前数据库副本上检查；切换失败会尝试恢复上一代码版本。**回退只切换代码，不用旧备份覆盖新数据。** 有数据库结构变化时还需独立证明旧代码可读写。本课实测 v0.9.2 → v0.9.1 → v0.9.2：两版差异为启动前配置校验，数据库结构一致；新增记录完整保留。后续 v0.9.3 只修正公网消息的访问说明。不要回退到本课已确认存在凭据权限问题的 v0.9.0，也不能据此认为任意历史版本均兼容。

记录位于本机 `.runtime/cloud-runs/<版本>/` 与服务器 `/root/alphaproject-lab-deploy/`；公网 `release.json` 可查看当前标识。备份包含用户数据，仅管理员可读，目前保存在同一台主机，没有异地容灾。网络中断后先查版本和服务状态，不凭本机缺少回执重复发布。

迁移后 `.runtime/cloud-primary.json` 会阻止本机启动同一学习数据库，避免两处重复执行通知或累计预算。开发验证使用临时测试库；日常直接打开公网地址。不要把这个标记当成数据同步工具。

## 定期数据库备份与私有恢复检查

v0.10.1 已安装独立 `alphaproject-lab-backup.timer`，每天北京时间 02:20 执行，保留最近 7 份校验通过且属于本工具的快照。新工具使用 SQLite 一致性在线备份，源以只读方式打开；完成后校验 SHA-256、完整性及外键，再原子发布。失败的新备份不会先删除旧好副本，未知、损坏或有额外文件的目录保留待查。原有 `backups/` 发布快照不参加新轮转。

只有已上线且公网核验通过的包可安装或更新运维工具：

```text
.venv\Scripts\python.exe -X utf8 deployment/cloud/deploy.py operations --package <当前版本包记录.json>
```

该命令持有原部署锁，核对当前版本，保护未知 unit/drop-in；把独立备份脚本固定到 `/opt/alphaproject-lab/operations/<脚本SHA-256>/backup.py`，因此代码回退不移除备份能力。先实际运行服务并确认本次新产物，再启用 timer；失败恢复只处理这两份 unit，不覆盖数据库，恢复失败明确记入回执。普通 `update` 保持现有固定工具及 timer；只有备份工具有变更时再显式执行上述 `operations` 命令。

## 服务器自动验收与结果通知

用户于 2026-10-22 要求将持续采集及茅台涨跌各 3% 的开盘验收迁到服务器。v0.10.2 提供独立的 `alphaproject-lab-acceptance.service` 与同名 timer，按北京时间工作日 09:35、15:35 检查；交易日资格仍由应用既有日历判断。任务固定到本次已校验发布目录，使用 `alphaproject-lab` 低权限用户，只加载现有飞书凭据，以 HTTPS GET 读取网站，不打开生产数据库、不调用模型。电脑与 Codex 不参与执行。

在代码包已准备、上线且公网验证通过后，运行：

```text
.venv\Scripts\python.exe -X utf8 deployment/cloud/deploy.py acceptance --package <当前版本包记录.json>
```

首次安装时，安装器持有部署锁，保护不属于本工具的 unit 与 drop-in。先启动真实服务并核对本次报告，再启用 timer、检查实际排期、写入安装记录，最后再次执行并核对唯一的迁移通知平台回执。只有以上步骤完成，才可结束旧的本机回查。安装失败恢复本次修改的两个 unit，移除本次新建且未被改变的安装记录；保留采样证据和通知账本，也不回滚生产数据。根部署状态目录要求管理员所有且为 0700。

已有固定程序的升级须先读回 `/root/alphaproject-lab-deploy/acceptance.json` 的当前 `release_id`，核对原安装和通知账本，再明确传入旧版本：

```text
.venv\Scripts\python.exe -X utf8 deployment/cloud/deploy.py acceptance --package <新版本包记录.json> --expected-observer <已核对的旧验收程序release_id>
```

旧版本不符、账本缺失、存在未知发送结果或原迁移回执无法对应时拒绝切换。升级保持最初 `installation.json.release_id`、`installed_at` 和 `receipt_key`，仅增加/更新 `runner_release_id`；独立管理回执记录 `updated_from`。先暂停旧 timer 并等服务空闲，切换后启用 timer，再核对本次真实运行与重复运行；可能的 Persistent 补起也必须有本次报告和服务成功证据。失败恢复旧 unit、运行绑定和管理记录，保留报告与通知状态；已结束的观察任务不会因升级自动重启。重复执行同一次已完成升级会读回既有结果，不重发迁移通知。当前 v0.10.4 升级来源为 `lab-20261021T195417756680Z`。

独立证据保存在 `/var/lib/alphaproject-lab-acceptance/`：`runs/` 留每次报告，`last-run.json` 是最近一次，`state.json` 保存累计结果，`notification-ledger.json` 保存发送意图与平台回执。目录 0700、文件 0600。管理员可用 `systemctl status alphaproject-lab-acceptance.timer` 和 `systemctl show alphaproject-lab-acceptance.timer -p TimersCalendar -p LastTriggerUSec -p NextElapseUSecRealtime` 查看排期；多条 `TimersCalendar=` 均须保留，不能按普通字典只取最后一条。

当前服务器每轮最多观察 6 次、相隔 65 秒，仍要求连续 3 次有效后台采集才能通过；无效/重复样本重置连续数，进程/发布、时段、规则或通知配置变化时停止，休市只观察一次并回看历史。探针预算 480 秒，systemd 服务截止 600 秒，达标即可提前退出。单独使用探针 CLI 时，只有显式提供 `--max-observations` 才改变其原观察上限；服务器运行器已传入 6。

正常休市、没有触线和结果不变时安静；首次连续采集通过、自然 3% 事件及其通知结果、实际故障或需用户处理时，才向原有私人飞书群发送结果。发送前持久化意图，平台已接受的消息不重复发送；中断或结果不确定时保留未知状态，不自动重发。任务记录实际启动/完成时间，并保存原始触发环境；只有当前 manager 的状态、InvocationID 与精确双时钟能够关联本次运行时，才认定 timer 触发。无法关联时保留 unknown，计划/触发时间为空；补起与计划推定单独标记，不冒充准点触发。

两个自然目标通过且对应结果通知获平台接受后写 `completed.json`；用户改变被观察的规则并完成相应通知后写 `suspended.json`。unit 条件使后续验收跳过，不影响应用原有采集、规则提醒或早盘简报。普通应用更新不会自动替换这份固定的验收程序；如需更换观察目标或脚本，先核对既有安装与账本，再执行明确迁移，不能通过删账本绕过去重。任务和应用在同一服务器，整机离线时无法即时向外报告。实际安装、去重及自然时点状态见[第二十二课](../../specs/015-operations/acceptance.md)。
